# 3ialna CLI release workflows

This guide documents the supported command-line paths for the `mgomma/3ialna` repository. The app is privacy-first: child profiles, requests, rewards, recordings, rules, and usage history remain on the device. CI must never print or upload those values.

## Prerequisites

Install Flutter, Dart, Java 17, Android SDK command-line tools, Git, and the GitHub CLI. Authenticate the GitHub CLI with access to `mgomma/3ialna`:

```bash
gh auth status
flutter doctor -v
```

Run all commands from the Flutter repository root:

```bash
cd /path/to/3ialna
```

## Local verification before pushing

Use the same checks that CI performs as far as the local machine supports:

```bash
flutter pub get
flutter analyze
flutter test --coverage
flutter build apk --debug
```

For a local release-signing check, create `android/key.properties` from `android/key.properties.example`. Keep the file and keystore outside Git. The Gradle configuration intentionally fails a release build when signing properties are missing. The debug-signing override is for local checks only:

```bash
flutter build apk --release -PallowDebugReleaseSigning=true
```

Do not use a debug-signed APK for Play Store publishing.

## Push changes to `dev`

Review the change, verify that no credential or child data is staged, then push:

```bash
git status --short
git diff --check
git diff --cached --name-only
# inspect staged files before committing
git add <files>
git commit -m "<short change description>"
git pull --rebase origin dev
git push origin dev
```

A push to `dev` can trigger the Flutter CI and Firebase App Distribution workflows when Android, Flutter, or dependency files change. Do not force-push the shared branch.

## Monitor GitHub Actions from the terminal

List recent runs:

```bash
gh run list --repo mgomma/3ialna --branch dev --limit 10
```

Watch a specific run:

```bash
gh run watch <RUN_ID> --repo mgomma/3ialna --exit-status
gh run view <RUN_ID> --repo mgomma/3ialna --log-failed
```

The CI workflow must complete analyzer and test jobs successfully before treating the change as ready. A successful Android artifact job does not override a failed test job.

## Manual Firebase App Distribution run

The Firebase workflow is an internal testing channel, not the Play Store release channel. It builds optimized, split-per-ABI evaluation APKs and publishes a public GitHub debug pre-release so the website can update its direct download metadata. Firebase upload is optional and requires these GitHub Actions secrets:

| Secret | Purpose |
|---|---|
| `FIREBASE_APP_ID` | Firebase Android App ID for package `com.ialna.app`. |
| `FIREBASE_SERVICE_ACCOUNT_JSON` | Complete service-account JSON, stored only as an Actions secret. |
| `FIREBASE_TESTER_GROUPS` | Optional tester-group alias. |

Trigger the workflow from the CLI:

```bash
gh workflow run firebase-app-distribution.yml --repo mgomma/3ialna --ref dev
gh run list --repo mgomma/3ialna --workflow firebase-app-distribution.yml --limit 1
gh run watch <RUN_ID> --repo mgomma/3ialna --exit-status
```

Never publish Firebase's short-lived `binary_download_uri` as a permanent website link. Use the GitHub release asset URL generated by the workflow. The current direct APK is an evaluation build and may require Android's per-app “install unknown apps” permission; keep Play Protect enabled.

## Signed Play App Bundle and Internal testing

The guarded `play-internal-release.yml` workflow is the production Android path. It always runs analysis and tests, requires a production upload keystore, builds `build/app/outputs/bundle/release/app-release.aab`, verifies the JAR signature, and uploads the AAB as a short-retention artifact. It uploads to Google Play Internal testing only when `publish_to_internal` is explicitly set to `true`.

Configure these GitHub Actions secrets only after the Play Console upload-key and Play App Signing arrangement is understood:

| Secret | Purpose |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | Base64 contents of the private production upload keystore. |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password. |
| `ANDROID_KEY_ALIAS` | Upload-key alias. |
| `ANDROID_KEY_PASSWORD` | Upload-key password. |
| `PLAY_SERVICE_ACCOUNT_JSON` | Google Play Developer API service-account JSON with the minimum release permissions. |
| `PLAY_PACKAGE_NAME` | Optional guard; if present, it must be `com.ialna.app`. |

Run a validation-only build first:

```bash
gh workflow run play-internal-release.yml --repo mgomma/3ialna --ref dev \\
  -f build_name=0.1.0 \\
  -f build_number=1 \\
  -f publish_to_internal=false
```

After the signed artifact has passed validation and the Play Console Internal testing track is ready, repeat with `publish_to_internal=true`. The workflow is deliberately fail-closed: missing signing secrets, an invalid package guard, a nonnumeric build number, or a failed test prevents publication.

For a local build, use the equivalent helper after placing a private `android/key.properties` and upload keystore on the machine:

```bash
scripts/build-play-internal-aab.sh --build-name 0.1.0 --build-number 1
```

The local helper never uploads to Google Play. Confirm the AAB checksum and test the Play-delivered artifact through Internal testing before promotion.

## Website release metadata

The Firebase workflow updates the website release metadata and dispatches the Pages deployment after a successful eligible build. If a release link needs to be refreshed manually, first confirm the GitHub release asset exists:

```bash
gh release list --repo mgomma/3ialna --limit 5
gh release view <TAG_OR_RELEASE> --repo mgomma/3ialna
```

Then run the repository's website-update helper if present, or use the website repository's documented metadata command. Review the generated diff, verify the URL returns an APK rather than an HTML page, and push only the generated metadata change.

## Manual workflow dispatch with explicit APK type

The CI workflow supports manual dispatch for the installable APK job. Review available inputs first:

```bash
gh workflow view flutter-ci.yml --repo mgomma/3ialna
```

Then dispatch with the workflow's declared inputs, for example:

```bash
gh workflow run flutter-ci.yml --repo mgomma/3ialna --ref dev
```

Do not invent workflow inputs at the command line; use the names shown by `gh workflow view`.

## Release safety rules

Do not commit `android/key.properties`, keystores, service-account JSON, Firebase tokens, `google-services.json` unless the app later requires it, or personal diagnostic exports. Before pushing, use:

```bash
git status --short
git grep -nE '(BEGIN PRIVATE KEY|ghp_|AIza|client_email|private_key)' -- ':!docs'
```

If a credential is exposed, revoke or rotate it immediately in the issuing console and replace the affected GitHub secret. Release artifacts must not contain child names, birth dates, gender, PINs, recordings, domains, usage history, or crash payloads.
